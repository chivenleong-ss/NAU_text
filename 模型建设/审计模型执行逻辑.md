# 审计模型执行逻辑

> 前面三份文件（规则清单 / 统一数据模型 / 字段来源清单）解决"数据长什么样、从哪来"。
> **这份文件解决"模型怎么跑、审出什么问题、怎么交叉验证坐实"**——是整个审计智能体的心脏。
>
> 一句话逻辑：**多源数据 → 规则引擎硬算出疑点 → 交叉验证引擎用"第二、第三个证据源"去印证 → 专家智能体定性定级 → 主审汇总出报告。**

---

## 一、模型整体架构（三层计算 + 数据流）

```
┌────────────────────── 原始数据（6 类）──────────────────────┐
│ ①分包合同(Word) ②结算台账(Excel) ③结算附表(Excel)           │
│ ④物资台账(Excel) ⑤施工日志(Word/纸质) ⑥业主结算清单(Excel) │
└────────────────────────────┬───────────────────────────────┘
                             │ 解析器 parser → 统一数据模型(中间表)
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 第一层：规则引擎 rule_engine（Python 确定性硬算，不用 LLM）    │
│   262 条制度规则 + 6 条逻辑关系规则 → 逐条比对 → 输出【疑点池】│
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 第二层：交叉验证引擎 cross_validator（多源印证）              │
│   一个疑点，至少拉第二、第三个数据源去印证，才从"疑点"升为   │
│   "坐实问题"，否则降级为"线索待核"。                          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 第三层：专家智能体 experts（LLM 语义定性，不做算术）           │
│   成本/合同/现场/材料/财务 5 个专家对坐实问题定性、归因、定级  │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 主审驾驶舱 lead_agent（汇总 + 综合判断 + 出审计报告）          │
└──────────────────────────────────────────────────────────────┘
```

**铁律**：算量、比价、比例、阈值 —— 全部 Python 硬算（可复现、可举证）；LLM 只做"这段合同条款是不是禁止签证"这类语义定性，和"组织语言写报告"。

## 二、审计问题点（模型到底能审出什么）

> 下面每个问题点 = 一条"证据链"：触发规则 → 数据证据 → 交叉印证 → 定级 → 处理建议。
> 前 6 个是 **A 项目真实数据里已埋设、模型能直接坐实**的问题；第 7 个是模型逻辑覆盖但当前缺横向数据。

### 问题点 1：安装工程结算超合同额 51.8%，缺"三重一大"决策与补充协议

| 项 | 内容 |
| --- | --- |
| **触发规则** | 规则一：最终结算额超合同额 5% 以内可不签补充协议；超 5% 需"三重一大"决策 + 补充协议 |
| **数据证据** | 结算台账：A-CWTZ-AZ-2022-04 合同价 100 万 → 审定金额（含税）151.84 万，**超 51.8%** |
| **交叉验证** | ① 审定金额 vs 合同价（超 51.8%，远超 5%）→ ② 回查 approval_decision 有无"三重一大"纪要 → ③ 回查 supplementary_agreement 有无补充协议 → **两者皆无 = 坐实** |
| **定级** | 🔴 高 |
| **处理建议** | 移交"三重一大"专项核查；要求补决策纪要 + 补充协议，否则按制度定性为超结/不规范 |

### 问题点 2：土方结算出现合同明令禁止的签证项

| 项 | 内容 |
| --- | --- |
| **触发规则** | 规则二：分包结算出现合同中明确禁止事项（不允许签证）→ 跑冒滴漏 |
| **数据证据** | 土方合同 A-SDQ-TF-2022-01 正文"无论何种情况，本分包工程无签证"；结算附表3 计价表"二、签证"出现 **SDQ-QZ-001 清淤泥 100m³ 10900 元** |
| **交叉验证** | ① 合同正文禁止签证条款 → ② 结算计价表出现签证行 → ③ 签证单签章是否完整 → ④ 业主结算有无"清淤泥"对应项（无 = 甲方也未认此量，进一步坐实虚假签证）|
| **定级** | 🔴 高 |
| **处理建议** | 该 10900 元剔除；签证单移交核查真伪；属典型跑冒滴漏 |

### 问题点 3：材料超耗未按合同扣款

| 项 | 内容 |
| --- | --- |
| **触发规则** | 规则三：材料超用额度超合同约定值，但结算单未扣除 → 跑冒滴漏 |
| **数据证据** | 主体合同损耗率钢筋≤2%、混凝土 0%、超耗按采购单价 150% 扣；物资台账：HPB300 预算 50.34t 领用 60.40t（**超 20%**）、HRB400 预算 2307.70t 领用 2446.16t（超 6%）、C15 预算 2637.46m³ 领用 2700m³（超 2.37%）|
| **交叉验证** | ① 领用量 vs 预算量算超耗率 → ② 对照合同损耗率上限 → ③ 查结算"扣款及罚款"栏（**为空 = 未扣**）→ ④ 反推应扣金额 = 超耗量 × 采购单价 × 150% |
| **定级** | 🔴 高 |
| **处理建议** | 补扣钢筋/混凝土超耗款；核对是否重复计取甲供材 |

### 问题点 4：未签合同先进场施工

| 项 | 内容 |
| --- | --- |
| **触发规则** | 规则四：合同签订日期晚于最早施工日期 2 个月，且未提供比价记录与进场单价承诺书 → 未签合同先进场 |
| **数据证据** | 主体/土方合同签订 2024-04-01；施工日记 2024-01-20 已开展 C15 浇筑（差 **2.4 个月**）|
| **交叉验证** | ① 合同签订日期 vs 施工日志最早施工日期（超 2 个月）→ ② 回查比价记录 → ③ 回查进场单价承诺书 → **两者皆无 = 坐实** |
| **定级** | 🔴 高 |
| **处理建议** | 定性未签合同先进场；追溯进场前成本是否失控 |

### 问题点 5：土方"清淤泥"清单外项（疑似虚假结算）

| 项 | 内容 |
| --- | --- |
| **触发规则** | 规则六：结算单出现分包合同清单外清单项，且业主结算无此项 → 虚假结算 |
| **数据证据** | 土方合同清单仅 4 项（基础钎探/挖土方/平整/回填方），**无"清淤泥"**；业主结算清单亦无此项 |
| **交叉验证** | ① 结算清单项"清淤泥" → ② 合同清单项无此项 → ③ 业主结算清单项无此项 → **三向比对，结算独有 = 坐实虚假** |
| **定级** | 🔴 高 |
| **处理建议** | 判定虚假结算项，剔除并追责 |

### 问题点 6：安装工程"劳务分包"却按 9% 税率结算（税务风险）

| 项 | 内容 |
| --- | --- |
| **触发规则** | 262 条制度规则中的税率/计税规则：劳务分包一般简易计税 3%，专业分包一般计税 9% |
| **数据证据** | 结算台账 A-CWTZ-AZ-2022-04：分包方式="劳务分包"，增值税率="9%"（同表主体工程劳务分包是 3%）|
| **交叉验证** | ① 分包方式（劳务）vs 税率（9%）矛盾 → ② 对照同表主体工程劳务分包 3% 作横向佐证 → ③ 核发票/计税方式 |
| **定级** | 🟡 中 |
| **处理建议** | 核查计税方式与发票，判断是否多计税金 |

### 问题点 7：同区域同类型主体劳务价格异常（规则五，当前缺横向数据）

| 项 | 内容 |
| --- | --- |
| **触发规则** | 规则五：同区域同类型项目三份主体劳务合同价格均值比该项目低 15% → 疑似套取费用 |
| **数据证据** | 需 A 项目之外、同区域同类型 ≥3 份主体劳务合同的清单单价 |
| **交叉验证** | ① 本项目主体劳务合同清单单价 → ② 同区域同类 3 份合同均值 → ③ 价差 ≥15% → 移交追责委 |
| **定级** | 🟡 中（待补数据）|
| **处理建议** | 补录横向合同数据后自动触发；当前 A 项目数据不覆盖 |

## 三、综合交叉验证：怎么从"单规则命中"到"坐实问题"

> 核心机制：**单一规则命中只能叫"疑点"，多源数据 + 多规则共振才能坐实。** 下面是交叉验证矩阵——每行一个疑点，每列一个数据源，格子 = 该数据源为这个疑点提供什么证据。

| 问题点 | 合同正文 | 结算台账 | 结算附表(计价表) | 物资台账 | 施工日志 | 业主结算 | 审批决策/补充协议 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 超结 51.8% | 合同价 100 万 | 审定 151.8 万 | — | — | — | — | **缺三重一大+补充协议** |
| 2 禁止签证却签证 | "无签证"条款 | — | 签证 10900 元 | — | — | 无"清淤泥" | 签证单签章 |
| 3 材料超耗未扣 | 损耗率 2%/0% + 150% 扣 | — | 扣款栏为空 | 超耗 20%/6%/2.37% | — | — | — |
| 4 未签合同先进场 | 签 2024-04-01 | — | — | — | 2024-01-20 已施工 | — | 缺比价记录/进场承诺书 |
| 5 清单外项 | 合同清单无"清淤泥" | — | 结算有"清淤泥" | — | — | 业主清单无此项 | — |
| 6 税率矛盾 | 分包方式=劳务 | 税率=9% | — | — | — | — | — |

**验证规则（可写成代码）：**
1. 每条疑点默认 `status = 疑点`；
2. 每命中一个**独立数据源**的证据，`evidence_count += 1`；
3. `evidence_count ≥ 2` → 升级为 `坐实`；`evidence_count = 1` → 保持 `疑点（待核）`；
4. 问题点 2 和 5 是"**三向比对**"（结算 vs 合同 vs 业主），天然 ≥2 源，直接坐实；
5. 坐实问题 → 交专家智能体定级定性 → 主审出报告。

## 四、模型代码模块划分（怎么构建）

| 模块 | 职责 | 输入 | 输出 | 技术 |
| --- | --- | --- | --- | --- |
| `parser/` | 6 类原始文件解析进统一数据模型 | 原始 Excel/Word/PDF | 中间表 JSON/DataFrame | pandas、python-docx、PaddleOCR |
| `rule_engine/` | 262+6 条规则确定性硬算 | 中间表 | 疑点池（结构化：问题ID/规则ID/字段/数值/阈值）| 纯 Python 函数 |
| `cross_validator/` | 多源印证，疑点→坐实 | 疑点池 | 带证据链的问题清单 | Python + 证据计数 |
| `experts/` | 5 个专家智能体语义定性定级 | 坐实问题 | 定性/归因/定级/建议 | LLM（Ollama/API）+ 提示词 |
| `lead/` | 主审汇总、综合判断、出报告 | 专家结论 | 审计报告 | LLM + 模板 |
| `rag/` | 制度问答（"超结 5% 依据哪条？"）| 用户提问 | 带条款引用回答 | 向量库 + LLM |

## 五、一条问题点的完整生命周期（举例：问题点 2）

```
1. 解析器：土方合同正文 → contract.no_variation_allowed = True
           土方结算附表3 → settlement_line_item[SDQ-QZ-001, category=签证, 10900元]

2. 规则引擎：规则二命中 → 疑点 {rule_id: R2, amount: 10900, status: 疑点}

3. 交叉验证：合同禁止签证(证据1) + 结算出现签证(证据2) + 业主无此项(证据3)
            → evidence_count = 3 → 升级为 坐实

4. 专家智能体(合同专家)：定性"违反合同禁止性条款，属跑冒滴漏"
   (现场专家)：签证单签章是否有效？是否真实发生？

5. 主审：汇总 → 审计报告："土方结算含禁止签证项 10900 元，建议剔除并追责，定级高"

6. RAG：审计员问"为什么禁止签证的合同还能出现签证？"→ 引用合同条款 + 制度条款回答
```
